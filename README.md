# Puget Sound Scenario Studio

Interactive scenario workbench for the Greater Seattle Regional Data Hub.
Pick a zoning scenario, move a few controls, and immediately see capacity,
constraints, and the evidence behind the result.

**Status: Phase 1 MVP.** Bel Red is the first and only study area. The code
is jurisdiction neutral from the first commit: districts, standards, study
areas, and assumptions all arrive as data files, so a second study area is
a data prep job, not a development job.

**Not built yet (later phases):** LUCA preset (Phase 2), Seattle expansion
(Phase 3), brief export (Phase 4), 3D massing (Phase 5), transit and cost
scenarios (Phase 6). The LUCA preset button in the UI is deliberately
disabled with an explanation until the draft LUCA standards are extracted.

## Run it

There is no build step. The app is static files.

```sh
# Serve the repo folder over HTTP (opening index.html from file:// will
# fail: the app fetches its data files, which browsers block from file URLs).
python3 -m http.server 8000
# then open http://localhost:8000/
```

## Reproduce the data

```sh
# Regenerate every file under data/ from the hub sources. Needs geopandas;
# the hub venv already has it.
~/workspace/your_files/regional-data-hub/phase2/venv/bin/python scripts/prep_belred.py
```

# Runs the exact model code the browser runs against the generated data.

## Architecture

### Module layout

| Path | What it is | Why it is separate |
|---|---|---|
| `index.html` | Page shell: header, three regions, drawer, settings panel, mobile section nav | Structure only; no logic, so the layout is reviewable on its own |
| `css/style.css` | All styling, no framework | A static page should be readable without a build step |
| `js/model.js` | Pure capacity model | No DOM, no map, no fetch, so Node can run the same code the browser runs and the acceptance test cannot drift from the app |
| `js/app.js` | State, settings, map, controls, results, drawer | Everything that touches the DOM or MapLibre lives here and nowhere else |
| `data/belred/parcels.geojson` | 463 study area parcels, EPSG:4326 | Small derived web data, generated by the prep script |
| `data/belred/zoning.geojson` | 19 BR-* zoning polygons | Map boundary layer |
| `data/belred/standards.json` | Dimensional standards per district, with citations, verification status, flags, and FAR exemption notes | The single source of truth for what the code allows |
| `data/registry.json` | Study areas and per-jurisdiction standards readiness | Honest coverage: Bel Red verified, Seattle partial, the rest not yet extracted |
| `data/validation.json` | Acceptance targets | The test compares against the CSV sums, not against prose |
| `scripts/prep_belred.py` | Converts hub GeoPackage + CSVs into `data/` | Repeatable: a hub refresh is one command, never a hand edit |
| `scripts/acceptance_test.js` | Node acceptance check | Runs `model.js` against the generated data; exit 0 is green |

### Data flow

```
hub sources (GeoPackage, standards CSV, capacity CSV)
        |
        v  scripts/prep_belred.py (one command, repeatable)
data/belred/*.json, data/registry.json, data/validation.json
        |
        v  fetch on page load (app.js: loadData)
js/model.js computeScenario(parcels, districts, scenario options)
        |
        +--> results panel totals (gross floor area, homes, jobs)
        +--> district table (acres, effective FAR, homes, jobs, flags)
        +--> constraints summary (plain-language active flags)
        +--> map (per-parcel properties stamped onto features, then painted)
        +--> detail drawer (parcel or district, with citations and badges)
```

The map never computes capacity. After each model run, `app.js` stamps
`contrib`, `constraint`, and `excluded` properties onto the GeoJSON
features and hands them to the MapLibre source. Color modes are paint
expressions over those properties, so switching modes never re-runs the
model.

### Layout: desktop and mobile

One stylesheet, no framework, three breakpoints:

- **Above 1100px (desktop):** the three-column grid: scenario controls
  left, map center, results right. Panels scroll internally; the page
  itself does not scroll.
- **760px to 1100px (tablet):** two columns (controls + map), with the
  results panel spanning the full width below.
- **760px and below (phone):** one scrolling column in this order: map
  (about 55% of the viewport tall, capped at 420px), results, scenario
  controls. A fixed section nav at the bottom (Map / Results / Scenario)
  jumps to each part in one tap; it is plain anchor links, so it needs no
  JavaScript and works with keyboard focus. The detail drawer becomes a
  bottom sheet (at most 72% of the screen tall) and the settings panel
  becomes a full-screen overlay. The district table scrolls sideways
  inside its own box, so the page never gains a horizontal scrollbar.
  Every tappable control is at least 44px tall on a phone, and the
  sliders get a taller track and a 28px thumb.

The layout is CSS only: `index.html` keeps the same ids and classes
`app.js` expects, and `model.js` and the data files are untouched by any
layout change.

### Scenario, comparison, and settings state

State is split three ways on purpose:

- **Scenario** (`{ presetId, opts }`): the control values the model runs
  on. Lives in the URL hash (`#s=` + base64url JSON), so a link restores
  the exact scenario. Any manual control change forks the active preset
  into a custom scenario.
- **Comparison**: a baseline preset, or a snapshot copy of a scenario.
  Lives in memory and in the URL hash next to the scenario. The results
  panel shows baseline totals and the delta against it.
- **Settings**: display and behavior preferences. Live in localStorage
  under `pss-settings-v1` and are applied on every load. A shared link
  always wins over the default-preset settings.

### The model (v2 method, unchanged)

Per candidate parcel: lot sq ft = lot acres x 43,560; effective FAR =
base FAR + participation x (max FAR - base FAR); gross floor area = lot
sq ft x effective FAR x net factor (0.85); residential sq ft = gross x
group residential share; homes = residential sq ft / 950; jobs =
non-residential sq ft / 350. Scenario totals are the summed capacity x
the realization rate. Districts with no incentive system have max FAR
equal to base FAR, so they always use base FAR with no special case in
the code. Capacity is gross, not net of existing homes or jobs. Height
is a flag, not a calculation input. FAR exemptions are displayed as
notes, never modeled.

## Controls: why each one exists

| Control | Why it is there |
|---|---|
| Presets (Base / Full incentives / 40%) | The three v2 bounds the tool must reproduce, in one click |
| Incentive participation slider | The policy variable: how much of the amenity system projects actually use |
| Realization rate slider | The buildout variable: the v2 comparison case is 50% |
| Sq ft per home / per job sliders | The conversion assumptions, so a user can test sensitivity |
| Net factor slider | The buildable share of gross floor area after circulation and structure |
| District checklist | Excluding a district removes it from totals and the map |
| Residential share overrides (advanced) | Test what happens if a district group builds more or less housing |
| Color mode (district / capacity / constraint / candidate) | See the same parcels by what drives the result, not just by zone |
| Compare against (baseline + snapshot) | Comparison is a first-class feature: the delta is the answer |
| Save / Load scenario | Scenarios are small JSON files; no accounts |
| Copy share link | The URL is the primary sharing route |
| District table sorting | Find which districts drive the result |
| Parcel and district detail drawer | Every number traceable to a source, citation, or stated assumption |

## Settings: why each one exists

| Setting | What it really changes |
|---|---|
| Default preset | Which preset a fresh visit (no shared link) opens on |
| Default realization rate | The realization a fresh visit opens on |
| Number rounding | Homes and jobs shown exact, or rounded to the nearest 10 / 100 |
| Floor area unit | Floor area shown in sq ft or million sq ft |
| Basemap style | Switches the raster basemap (light / dark / OpenStreetMap) |
| Show zoning boundaries | Shows or hides the zoning outline layer |
| Show non-candidate parcels | Shows or hides parcels that failed the redevelopment screen |
| Show verification badges | Shows or hides the reproduction-only badges in the drawer |
| Show code citations | Shows or hides citation and source-basis text |
| Show constraint flags | Shows or hides the flags column and flag badges |
| Show gross floor area | Shows or hides the floor area row in results |
| Show delta vs comparison | Shows or hides the delta rows in the comparison block |
| Sort districts by | Re-sorts the district table (homes / jobs / acres / name) |

Settings persist in localStorage. Resetting them restores defaults.

## Provenance and honesty

- Code snapshot date **2026-11-09** (Bellevue Land Use Code LUC
  20.25D.080 Chart A and LUC 20.25D.090) appears in the results footer.
- BelRed Look Forward LUCA: **draft, not adopted**.
- Capacity is **gross**, not net of existing homes or jobs, wherever
  totals appear.
- Known gaps are visible in the app, not buried in docs: the BR-MO vs
  BR-MO-1 swing, the unrecovered chart footnotes (11), (13), (15), the
  chart grid reproduction basis, and the absence of any numeric density
  limit in the code as read.
- Values resting on the chart reproduction without a separate official
  document are badged in the district drawer.
- The hub's large GeoPackages stay out of this repo. Only app code, prep
  scripts, standards tables, and small derived web data are versioned
  here.

## Dependencies

- **MapLibre GL 4.7.1**, loaded from the unpkg CDN in `index.html`
  (pinned version; no API key needed). This is the only dependency.
  There is no npm package, no build tool, and therefore no lockfile to
  commit; if a dependency is ever added, it gets pinned and the lockfile
  committed with it.
- **Python prep script**: geopandas, already present in the hub venv.
  No other Python packages.

Boring tech first: the stack is the standard library, MapLibre GL (named
in the design spec), and the hub's existing geopandas venv. No new
dependency was added for this build, and none should be added without
asking first.

## Security

- No API keys, tokens, or credentials anywhere in this repo, in code,
  config, or docs. No `.env` files are committed (`.gitignore` blocks
  them). The MVP needs no keys; if an external service ever needs one,
  it must come from environment at runtime.
- All inputs are validated before they touch the model: scenario JSON
  from a URL hash or a loaded file is type- and range-checked, and
  invalid input is rejected with a logged message and a visible error.
- No `eval` anywhere. Untrusted strings (parcel addresses, scenario
  names) are HTML-escaped before display.
- Nothing secret is written to logs.

## Accessibility

Semantic HTML throughout (header, main, sections, table with headers,
labeled controls). All controls are keyboard reachable, focus is visibly
outlined, the district table rows are keyboard operable, and the drawer
and settings panel close with buttons. Color is never the only signal:
flags and badges carry text.
